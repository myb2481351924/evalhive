# 项目方案：EvalHive —— 面向 CI/CD 的 LLM 评测与回归门禁平台

> 定位：简历项目。一句话故事线——"把测开的回归测试/CI 门禁方法论迁移到大模型质量保障上"。参考 promptfoo（声明式配置+CI 门禁）与 RAGAS（指标体系），用 Python 全栈实现。工作目录 `D:\training-agent`（当前为空）。

## 1. 核心能力（对齐简历卖点）

1. **声明式评测配置**：YAML 定义 `providers`（被测模型/应用）× `datasets`（用例集）× `assert`（指标）。
2. **三层指标体系**：
   - 确定性断言：exact/regex/json-schema/latency/cost 阈值——不花 API 钱，适合 CI 快速门禁；
   - LLM-as-Judge：正确性、相关性、有害性（可配 judge 模型与温度，记录 judge 原始输出保证可审计）；
   - RAG 指标：faithfulness（答案是否被上下文支持）、answer relevance，简化 RAGAS 实现。
3. **回归对比与基线**：两次 run 逐用例 diff、总分漂移、bootstrap 置信区间，可 `set-baseline`；退化超阈值即失败。
4. **CI 门禁**：`evalhive run --gate` 失败返回非零退出码 + Markdown 结果摘要（供 PR 评论），附 GitHub Actions 模板。
5. **可离线演示**：内置 `mock://` provider（录制的假响应），无 API key 也能跑通全流程——面试现场演示的关键。
6. **Web API + 简易前端**：项目/数据集/run 的 REST API，一个静态页用 ECharts 展示分数趋势与版本对比。

## 2. 技术栈

Python 3.11+、Pydantic v2（配置与结果模型）、Typer（CLI）、FastAPI + Uvicorn（API）、SQLAlchemy 2 + SQLite（可切 Postgres）、httpx（调用 OpenAI 兼容 API）、Jinja2（HTML 报告）、uv（依赖管理）、pytest + GitHub Actions。

## 4. 数据模型（SQLite）

- `Project`（name, baseline_run_id）
- `Dataset`（project_id, version_hash, path）
- `Run`（project_id, config_hash, started_at, status, summary_json）
- `CaseResult`（run_id, case_id, prompt, response, metric_name, score, passed, cost, latency_ms, judge_raw）

关键不变量：`config_hash = sha256(config + dataset_version)`，同 hash 可命中结果缓存（LRU + 文件缓存），省钱且可复现——这是简历上"可复现性"的谈资。

## 5. 实施步骤（按里程碑提交 git）

- **M1 骨架与引擎（核心）**：项目脚手架、YAML 配置模型、provider 抽象（openai/mock）、确定性指标、runner 并发执行、JSONL 数据集加载；产出 `evalhive run examples/rag-chat.yaml` 可出分。
- **M2 指标补全**：LLM-as-Judge（含 prompt 模板与解析兜底）、两个 RAG 指标、cost/latency 统计。
- **M3 回归与门禁**：run 存储、`diff`、bootstrap 置信区间、`set-baseline`、`--gate` 退出码、JUnit XML + Markdown 摘要、GitHub Actions 模板。
- **M4 HTML 报告 + CLI 打磨**：Jinja2 报告（用例明细、失败 Top、指标雷达图）、`typer` 帮助与补全。
- **M5 Web API + 前端**：FastAPI CRUD + 异步触发评测 + SSE 进度；ECharts 趋势/对比页。
- **M6 工程化收尾**：pytest 覆盖核心逻辑（指标计算、diff 统计、缓存 key）、Docker compose 一键起服务、README 定稿（含"设计决策"一节：为什么 mock provider、为什么 bootstrap——面试问答弹药）。

## 6. 验证方式

1. `uv run pytest` 全绿（含 mock 端到端：跑评测→diff→gate 失败路径）。
2. 无 API key 环境下 `evalhive run examples/mock-demo.yaml --gate` 正常出分、生成 HTML 报告。
3. `docker compose up` 后浏览器打开前端能看到趋势图。
4. 用 judge 模式跑一遍真实示例（可选，需用户自备 OpenAI 兼容 key）验证指标合理性。

## 7. 范围边界（明确不做）

不做用户体系/多租户、不做评测集自动合成、不训练模型（UI-TARS 那类不碰）；judge 指标只做 3 个有代表性的，不堆数量。这些留作 README"Roadmap"章节，反而体现规划能力。
